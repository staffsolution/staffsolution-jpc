## ■分類（タグ）

- 面接チェックシート（やめない仕組み内）
- 改善理由・改善目的への「あるある事例」

- 勘違いのその場説明パターン
- 改善結果の数値化（面接人数・ミスマッチ割合）
- 面接で得た情報→採用LP／仕組みへの転用

- ブロック単位で完成させる進め方

## ■現状（Before）

- 1028のフィードバックを受け、辞めない仕組み内の面接チェックシートに、改善理由・改善目的・項目ごとの成果などを追加した段階。
- 方向は合っている。改善理由と改善目的の追加、項目ごとの成果、バディ／Googleフォーム／損失の追加方針も良い。
- 一方で、面接チェックシートの箱だけを見ると、次がまだ薄い。
  - 「何を期待して応募したか」などの項目に、**よくあるミスマッチ事例（あるある）**が足りない。
  - 「現場が早く終わっても給料1日保証」など、**どう理解されていたか**の具体が薄い。
  - 勤務条件への対応可否・希望・不安を聞くことで、**持病や家庭事情が間接的に出る**、という狙いの説明が弱い。
  - 間違った認識があったときに、**その場でどう説明するか**のパターンが少ない。
  - 改善結果が「実感はあるが定量未検証」で止まっており、これまでの面接実績ベースの数字が置けていない。
  - チェックシートそのものの定義（何枚・誰が聞く・どう深掘るか）が薄い。
- 内容全体の水準は高い。直すのは「あるある・聞き方の狙い・数値・定義・LPへの転用」の肉付け。

---

## ■問題の本質（重要）

面接チェックシートの改善は、「質問を変えた」だけでは伝わらない。読み手が欲しいのは次の流れ。

```
1. なぜその聞き方にしたか（あるあるのミスマッチ／間接質問の狙い）
2. 間違っていたら、その場でどう説明するか
3. 実際に面接した人数・ミスマッチの割合など、数字での結果
4. 面接で得た情報を、採用LPや仕組みの改善にどう使ったか
```

「改善した結果、ミスマッチが減った実感はある」だけでは、再現できる打ち手に見えない。  
**あるある → 確認と説明 → 数字 → LP／仕組みへの反映** まで落とすと、同じチェックシートが「選んで採用する仕組み」になる。

また、抽象的な答えをそのまま受け取らず、**深掘りして深層を取る**のが面接の本体。チェックシートは質問リストではなく、その運用の型として定義する。

## ■ズレ（思考 or 設計）

| 取れている | まだ薄い／足す |
|---|---|
| 1028指摘どおり改善理由・目的を追加 | 理由の中に「あるある事例」が足りない |
| 改善後の聞き方（希望・不安など） | 改善後本文に、その聞き方が反映されているか不明瞭 |
| ミスマッチ防止の方向 | どう勘違いしていたか／その場の説明パターン |
| 間接質問の意図（持病・家庭事情） | 「直接聞かず出してもらう」狙いの明示 |
| 改善結果の実感 | 面接人数・ミスマッチ割合などの定量 |
| 「定量未検証」の正直さ | これまでの実績ベースで置ける数字があるはず |
| チェックシート改善そのもの | 誰が・何枚で・どう深掘るかの定義 |
| AI壁打ちの追加案 | 鵜呑みにせず、自問自答で肉付けする前提 |

- 骨格は1028の続きとして良い。ズレは「事例・聞き方の狙い・数字・運用定義・転用」が空いていること。
- 改善結果に書いた中身の一部は、改善理由側のあるあるに移した方が読みやすい。

## ■改善内容（What）

### 0. 維持してよい点

```
【良い】
・1028の指摘を受けて、面接チェックの改善理由・目的を追加している
・項目ごとの成果や、バディ／フォーム／損失の追加方針も合っている
・内容全体の水準は高い（喜ばれる方向）
```

直すのは面接チェックシートの箱の肉付け。他ブロックは、この箱を完成させてから。

### 1. 改善理由に「あるあるのミスマッチ事例」を入れる

「何を期待して応募したか」など、仕事をする上での目的を確認する項目では、**こんなはずじゃなかった**が起きやすい事例を置く。

| 入れるもの | 例 |
|---|---|
| あるある事例 | 求人票・採用LPの文言を、求職者がどう誤解しやすいか |
| 理解のされ方 | 「現場が早く終わっても給料1日保証」を、どう理解していたか |
| 面接での役割 | LPに書いてあっても勘違いがある → 面接で確認し、その場で説明する |

```
【あるある】
採用LPに「現場が早く終わっても給料は1日保証」と書いてあっても、
こう誤解しているケースがある（例：○○だと思っていた）

【面接でやること】
その理解を確認する
　↓
正しければ短く終える
　↓
ズレていれば、このパターンではこう説明する
```

あるあるは複数あってよい。改善結果側に書いてある理解ズレの話は、**改善理由の上の方へ寄せる**と流れが自然になる。

### 2. 間接質問の狙いを明示する（希望・不安の聞き方）

勤務条件への対応可否や、仕事に対する希望・不安を確認する方法に見直した、という改善は良い。  
次は「なぜその聞き方か」をはっきり書く。

```
【直接聞くと出にくい】
持病の不安、家庭の事情など

【間接的に聞く】
勤務条件への対応可否／希望／不安

【その結果】
もともと持っている不安や、家庭の事情を自分から話してくれることが多い
　↓
だからこの項目を追加している
```

改善後のチェック項目側にも、この聞き方が**本文として反映されているか**を確認する。理由だけ書いて改善後に無い、というズレをなくす。

### 3. 「正しければ短く／ズレたら説明」の運用を書く

それぞれの確認項目に、次の型があるとわかりやすい。

```
ちゃんと理解している → すっと終わる
勘違いしている → こういうケースのときは、こう伝える
```

仕事の理解（ホームページ・採用LPの読み取り）は特に重要。  
よくある勘違いと、その場の解説文をセットで置く。

### 4. チェックシートの定義と深掘りの型を足す

質問リストだけにしない。次を定義する。

| 定義する項目 | 例 |
|---|---|
| 形式 | A4ペラ1枚に質問項目がある、など |
| 誰が聞くか | 社長／浦川さん、など実態に合わせる |
| 深掘りの型 | 抽象的な答え → 具体を聞く → 深層心理を把握する |

特に「仕事の理解」「これまでの経験」は深掘りが効く。  
応募理由・希望不安・前職の退職理由のどこで希望／不安を深掘るかも、運用として明示する。

### 5. 改善結果は「実感」ではなく実績ベースの数字にする

「採用後のミスマッチや早期離職が減った実感はあるが、比較データがなく定量未検証」は正直だが、弱い。  
これまでの面接実績で置ける数字に置き換える。

```
例（実態の数字に合わせる）
・これまで約10人面接した
・そのうちミスマッチに該当したのは○人（○割）
・入社してもすぐ辞めそうなタイプが、面接時点でこのぐらい見えた
```

数字がなくても、「未検証」で止めず、**面接した回数と、そこで見えた割合の感覚値**まで書く。

### 6. 面接で得た情報 → 採用LP／仕組みへの転用を書く

改善結果に入れてほしいのは、「チェックして弾いた」だけではない。

| 面接で分かったこと | 転用の例 |
|---|---|
| 採用LPの理解度が低い／誤解が多い | LP側をわかりやすく直した |
| 想定していなかった希望・懸念 | ページ上で目立つように強調した |
| 求職者が求めていること／不安がっていることの偏り | その情報を前面に出すよう調整した |
| 新たに見えた現場の課題 | 会社の仕組みとして追加した |

```
深く聞いた
　↓
LPの改善ポイントが見つかった／求職者の本音が分かった
　↓
ページや仕組みに反映した
```

この循環があると、チェックシート改善が「採用の仕組み全体の改善」に見える。

### 7. AI壁打ちは参考。完成は自問自答で

AIが出した案（例：チェックシート変更だけでは採用担当との認識ズレが残る → 採用方針・基準の共有も入れる、など）は、参考にしてよい。  
ただしそのまま使わず、**浦川さん自身が自問自答して正しいところだけ肉付けする**。山本側で全部やるより、壁打ち主体で進めた方が定着する。

### 8. 進め方：ブロック単位で完成させる

このブロックは直す箇所が多い。  
一気に全部ではなく、**面接チェックシートを完成させてから、次のブロック（バディ／フォームなど）**へ進む。

## ■改善理由（Why）

- 1028で求めた「改善理由・定義・結果の一段」の、面接チェック側の具体化が今回の本題。
- あるある事例がないと、「なぜその質問にしたか」が抽象のまま残る。
- 間接質問の狙いを書かないと、「希望・不安を聞く」がただの確認項目に見える。
- その場の説明パターンがないと、面接官が変わったときに再現できない。
- 「定量未検証」のままでは、対策ごとの成果（1028指摘）が埋まらない。面接実績の数字で十分足りる。
- 面接で得た情報をLP／仕組みに戻すと、チェックシートが単発のツールではなく、やめない仕組みの一部になる。
- ブロック単位の方が、品質を落とさず進められる。

---

## ■改善後イメージ（After）

```
1. 改善理由：あるある事例（どう誤解していたか）＋間接質問の狙い
2. 改善後：その聞き方が本文に反映されている
3. 運用：正しければ短く／ズレたらこの説明、＋深掘りの型
4. 定義：何枚・誰が聞く・どこを深掘るか
5. 改善結果：面接○人中ミスマッチ○人、など実績ベース
6. 転用：面接で得た本音 → LP強調／仕組み追加の事例
```

音読して、「なぜこの聞き方？」「ズレたらどうする？」「数字は？」「その情報はどこに活きた？」で止まらない状態。

---

## ■やりがちなミス

- 改善理由に「確認する必要があった」だけ書き、あるある事例を置かない
- LPに書いてある前提で、求職者の誤解パターンを想定しない
- 希望・不安を聞く、とだけ書いて「間接的に持病や家庭事情が出る」狙いを省略する
- 改善理由には書いたのに、改善後の項目本文に反映されていない
- 「正しければ終わり／ズレたら説明」の運用を書かず、質問リストで止める
- チェックシートの形式・誰が聞く・深掘りの型を定義しない
- 改善結果を「実感はあるが未検証」で止め、面接実績の数字を置かない
- 面接で得た情報を弾く用途だけにし、LP／仕組みへの転用を書かない
- AIの壁打ち案をそのまま貼り、自問自答で検証しない
- 面接・バディ・フォームを同時に直し、どれも中途半端にする

## ■他の案件でも使えるパターン

### パターンA：改善理由には「あるある」を先に置く

```
よく起きる誤解・失敗
　↓
だからこの確認項目が必要
　↓
面接ではこう確認し、ズレたらこう説明する
```

抽象の「必要だった」より、事例の方が説得力が上がる。

### パターンB：直接聞きにくいことは間接質問にする

```
直接聞くと出にくい本音
　↓
希望・不安・対応可否として聞く
　↓
自分から話してもらう
```

採用・ヒアリング全般で使える。

### パターンC：改善結果は「実感」ではなく「○人中○人」

```
実施した回数
　↓
そこで見えた割合・件数
　↓
その情報を次にどう使ったか
```

厳密な対照実験がなくても、実績ベースで置ける。

### パターンD：現場で得た情報は、必ず広告／LP／仕組みに戻す

```
面接・ヒアリングで分かった本音
　↓
ページの強調／説明の修正／仕組みの追加
```

チェックやヒアリングが、単発で終わらない。

### パターンE：ブロック単位で完成させてから次へ

直す箇所が多いときほど、1箱を音読して「なぜ？」「結果は？」で止まなくなってから次の箱へ進む。

## ■1028・1021との関係

- 1021：Who除外は良い。次は実績ビフォーアフター。
- 1028：やめない仕組みの骨格と強い数字が出た。理由・定義・結果深掘り・対策ごと成果を足す段階。
- 今回：そのうち**面接チェックシート**の箱を具体化。あるある・間接質問・数字・転用・運用定義が宿題。
- バディ／Googleフォーム／損失の箱は、面接チェックを完成させてから同じ型で進める。
- 引き継ぐこと：価格対比・1名増員シミュ・成果報酬前のクライアント条件は、実績箱と別トラックで継続。
